# Parsing quality

[M1-08] measures how good the parser actually is, with a number, before
anything downstream is built on top of it. [M1-08b] re-runs the same
measurement after [M1-04c] (boundary/heading-detection fixes) and [M1-05b]
(the real LLM classifier replacing the stub) landed. [M1-08c] re-runs it a
third time after [M1-04d] (a vision-LLM boundary-escalation pass) landed —
and, finding that pass net harmful, disables it, fixes the failure it was
meant to address in the deterministic detector instead, re-measures, and
finally corrects the boundary criterion itself after showing that most of
the residual gap was the metric asking a flat question about a hierarchical
structure. All measurements and intermediate states are kept below in full
— none overwrites an earlier one, so the before/after story stays visible.

**Headline numbers, and which definition they are under.** The project's
current figures are **98.0% boundary / 92.0% type**, measured under the
corrected boundary criterion (see the fourth state below), with a
conservative reading of 96.0% boundary if one disputed sample is excluded.
Under the *original*, un-clarified criterion the same corpus measures
**84.0% / 86.0%**. The earlier 60.0% and 82.0% boundary figures were taken
under that original criterion and are not directly comparable to 98.0%. The raw evaluation data each measurement summarizes is committed
separately, not just as tables here: the annotated samples live in
[`eval/parsing_quality_sample.csv`](../eval/parsing_quality_sample.csv)
(current state is the third measurement's; the first and second
measurements' versions are recoverable from git history) and the computed
results in
[`eval/parsing_quality_results.md`](../eval/parsing_quality_results.md),
generated by `scripts/sample_parsing_quality.py` and
`scripts/score_parsing_quality.py` respectively (`make
sample-parsing-quality` / `make score-parsing-quality`).

**Validation method differs between the first measurement and the two that
followed it.** [M1-08]'s 50 clauses were checked by a human against the
source PDFs. [M1-08b]'s DoD also describes this as a manual step, but for
this project the project owner made an explicit, informed decision to
replace that manual pass entirely with an automated LLM judgment instead:
`google/gemini-3.7-flash` looks at the actual rasterized PDF pages around
each sampled clause's recorded boundary and independently judges boundary
correctness, clause type and provenance — the same three judgments a human
reviewer would make — via `scripts/validate_parsing_quality_sample.py`
(`make validate-parsing-quality-sample`). There is no separate human
review of the second or third measurement's sample. This is a real
methodological difference from [M1-08], stated here rather than left
implicit: the second and third measurements' numbers reflect an LLM's
judgment of the parser's output, not a human's.

## Method (2026-08-18 — first measurement, v4 corpus, classifier stub)

At the time of sampling, the built corpus
(`build/parsed_clauses.jsonl`/`.parquet`, `schema_version=v1`,
`clause_segmentation_version=v4`) held **4266 clauses across all 30
documents**.

**Sampling.** 50 clauses, stratified in two stages:

- **Stage 1 — a census, not a sample.** The corpus has only 19
  rule-assigned clauses (`type_source=rule`) in total, so all 19 are
  included unconditionally. Sampling a subset of an already-small
  population would only add sampling error for no benefit; a census
  measures rule-assigned accuracy at full population coverage.
- **Stage 2 — a stratified top-up of 31 clauses**, necessarily all
  LLM-assigned (the rule population is exhausted by Stage 1), drawn from a
  fixed quota over `(product_line, extraction_mode)`: CASCO/text 9,
  RCF-A/text 3, RCF-A/ocr 5, ASSIST/text 3, ASSIST/ocr 5, GAR.EST/text 3,
  CARTA VERDE/text 3. Each multi-era cell's quota is split across the four
  filing-year vintage buckets (2004–2009, 2010–2016, 2017–2021, 2022–2025 —
  the same buckets used in
  [`DATA_SOURCES.md`](DATA_SOURCES.md#resulting-composition)) by the
  largest-remainder method, then drawn with a fixed seed (`SEED=42`) for
  reproducibility.

Resulting sample: product lines CASCO 24 / RCF-A 10 / ASSIST 9 / GAR.EST 4 /
CARTA VERDE 3; extraction mode text 40 / ocr 10 (a deliberate oversample —
9.7% of the corpus is OCR, 20% of the sample is, so the OCR accuracy split
isn't computed from n≈5); type_source rule 19 / llm 31; all 4 eras present.

**Stated corpus gap, not a sampling artifact:** no rule-assigned clause in
the whole corpus is OCR-derived, so an "OCR ∩ rule-assigned" accuracy cell
does not exist to measure.

**Manual validation.** Each of the 50 clauses was checked by hand against
its source PDF (`data/policies/raw/`), recording three independent
judgments per clause:

- **Boundary correct** — does the clause, on the page range the parser
  recorded, start and end where it should in the PDF (not merged with a
  neighboring clause, not cut off mid-content, not misattributed to the
  wrong page range)?
- **Reference clause type** — the reviewer's own classification of the
  clause (`coverage` / `exclusion` / `condition` / `definition` /
  `procedure` / `other`), judged independently of what the parser
  predicted, then compared against it.
- **Provenance correct** — do the document/insurer/CNPJ/product
  line/indemnity regime/filing year attached to the clause actually match
  the source PDF?

## Results (2026-08-18 — first measurement, v4 corpus, classifier stub)

- **Boundary accuracy: 60.0% (30/50)**
- **Type accuracy: 40.0% (20/50)**
- **Provenance accuracy: 100.0% (50/50)**

Provenance is exactly as reliable as expected — it is attached once per
document from `manifest.csv` (frozen in [M1-05]), not derived per clause,
so a correct manifest row propagates cleanly to every clause underneath it.
Boundary and type accuracy are the real findings of this exercise.

### Confusion matrix (reference type × predicted type)

| reference \ predicted | coverage | exclusion | condition | definition | procedure | other |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| coverage | 2 | 0 | 0 | 0 | 0 | 3 |
| exclusion | 0 | 4 | 0 | 0 | 0 | 5 |
| condition | 0 | 0 | 1 | 0 | 0 | 12 |
| definition | 0 | 0 | 1 | 7 | 0 | 4 |
| procedure | 0 | 0 | 0 | 0 | 3 | 4 |
| other | 0 | 0 | 1 | 0 | 0 | 3 |

The matrix has almost no off-diagonal confusion between real types — the
rule pass practically never mislabels a `coverage` clause as `exclusion` or
vice versa. Nearly all the error mass is in one column: real clauses of
every type collapsing into predicted `other`. That is not a classifier
struggling with an ambiguous case — see the failure modes below.

### Rule-assigned vs LLM-assigned type accuracy

| type_source | n | boundary accuracy | type accuracy |
| --- | ---: | ---: | ---: |
| rule | 19 | 68.4% (13/19) | 89.5% (17/19) |
| llm | 31 | 54.8% (17/31) | 9.7% (3/31) |

The rule pass, where it fires, is genuinely good (89.5% type accuracy). The
"LLM" pass is not a classifier — see [Failure mode 1](#1-the-llm-classification-pass-is-a-stub-not-a-classifier).

### OCR-derived vs text-derived accuracy

| source | n | boundary accuracy | type accuracy |
| --- | ---: | ---: | ---: |
| text | 40 | 65.0% (26/40) | 47.5% (19/40) |
| ocr | 10 | 40.0% (4/10) | 10.0% (1/10) |

OCR-derived clauses are worse on *both* axes, not just type (which the
classifier-stub gap alone would explain). Boundary accuracy drops from 65%
to 40% — heading detection on OCR pseudo-lines has no font/position signal
to fall back on (see `clause_segmentation.py`'s OCR-pattern-only detection
tier), so boundary errors compound with the classification gap for this
9.7%-of-corpus, 2-document population.

## The three worst failure modes (first measurement)

Ranked by frequency across the 36 of 50 clauses with at least one incorrect
judgment (full table in
[`eval/parsing_quality_results.md`](../eval/parsing_quality_results.md#failure-mode-frequency)):
`classifier_stub` 18, `heading_missed` 8, `truncated_boundary` 7,
`merged_with_neighbor` 2, `wrong_type_ambiguous_heading` 1.

### 1. The LLM classification pass is a stub, not a classifier

`NullClauseClassifier` (`app/src/infrastructure/parsing/null_classifier.py`)
always raises `NotImplementedError`; the classification use case catches
that and force-assigns `clause_type=other`, `type_source=llm`,
`confidence=0.0` to every clause the rule pass doesn't match. This is not
"the LLM guessed wrong" — no model call happens. Across the **full built
corpus** (not just the sample), **4247 of 4266 clauses (99.6%) carry this
stub `other` label**; in the sample, 18 of 50 clauses were tagged
`classifier_stub`, and llm-assigned type accuracy is 9.7% (3/31) purely
because 3 of those 31 clauses happened to have a true type of `other`
anyway.

**Example** — sample #7, clause `3:condicoes-particulares-clausula-particular-1-ampliacao-do-ambito-de-cobertura`
(doc 3, AKAD, CASCO, page 25): a clause titled "AMPLIAÇÃO DO ÂMBITO DE
COBERTURA" that expands geographic coverage scope — unambiguously a
`coverage` clause — is labeled `other` because its heading doesn't match
any of the 13 patterns in `data/parsing/clause_type_mapping.csv` and the
LLM fallback never runs.

**Downstream cost.** `clause_type` is the metadata this whole system is
supposed to filter and cite by — coverage vs. exclusion is the single most
safety-critical distinction here, since [`SCOPE.md`](SCOPE.md)'s
`compatible`/`incompatible`/`insufficient_information` verdict depends on
telling the two apart. Today that distinction is backed by real
classification for **19 of 4266 clauses (0.45%) in the whole corpus**.
Any retrieval or citation logic that filters by `clause_type` is currently
filtering on a signal that is present for less than half a percent of the
corpus. **Follow-up: [M1-05b]** (already scoped, not implemented here).

### 2. Undetected headings misnest clauses under the wrong parent

The heading detector misses a genuine section heading, so the clause that
should start there gets absorbed as a child of whatever heading came
before it instead of becoming its own node. The clause's own text is often
intact — the *hierarchy* is wrong.

**Example** — sample #13, clause `11:clausula-de-assistencia-24-horas/2-5`
(doc 11, Porto Seguro, pages 52–53): the heading `CLÁUSULA 76R – DANOS A
VIDROS E RETROVISORES, LANTERNAS E FARÓIS – LIVRE ESCOLHA` on page 52 was
never detected, so a full glass-exclusions list (items a–gg of "2.
Exclusões gerais de vidros") ends up nested under `CLÁUSULA DE ASSISTÊNCIA
24 HORAS` — an unrelated roadside-assistance clause several sections
earlier. A second, structurally identical case: sample #26/#27/#30 (doc 20,
KOVR, OCR) — definitions `2.10` and `2.11` and condition `5.4` all get
misnested one level too deep, under sibling `2.1`/`5.1` instead of their
real parent section, because the OCR-only heading path has no font signal
to distinguish a real section break from a numbered sub-item.

**Downstream cost.** `bundle_section` is a required retrieval filter and
citation field ([M1-06]). A misnested clause inherits the wrong
`bundle_section`, so a query correctly scoped to one coverage bundle can
silently miss clauses that belong to it, or pull in clauses that don't —
the same wrong-document-retrieval risk
[`DATA_SOURCES.md`](DATA_SOURCES.md#same-insurer-pairs) documents at the
whole-document level, now shown to also occur *within* a single document's
own structure.

### 3. Clause boundaries truncate before the real content

The opposite failure from #2: the clause node is created in roughly the
right place, but its captured text stops short — sometimes at zero
characters — instead of covering the section that follows the heading.

**Example** — sample #19, clause `15:condicoes-gerais` (doc 15, MAPFRE,
page 13): the heading `CONDIÇÕES GERAIS` — a major structural section, not
a minor subclause — was detected, but the parser captured **0 characters**
of body text. Related, sharper cases in the same document: sample #23
(`RISCOS EXCLUÍDOS`, page 120) captured only the two-character list marker
`"i."`, and sample #21/#22 (`COBERTURAS BÁSICAS` / `COBERTURAS ADICIONAIS`,
pages 59/62–63) cut off mid-sentence at 70 and 215 characters. All four are
from the same 2004-vintage, pre-M1-04b-fix document, consistent with the
"legacy layout" difficulty already flagged in
[`DATA_SOURCES.md`](DATA_SOURCES.md#known-limitations).

A rarer but more severe variant of the same underlying gap (undetected
subsequent headings) runs the other direction: sample #16, clause
`13:riscos-excluidos` (doc 13, Zurich, pages 72–91) absorbed **20 pages and
over 41,000 characters** — several distinct coverage, condition and
exclusion sections — into one node still labeled `exclusion`
(`merged_with_neighbor`, 2 occurrences in the sample).

**Downstream cost.** A near-empty clause is a semantically inert retrieval
chunk — an embedding of `""` or `"i."` carries no signal, so a query that
should retrieve the real exclusions list under `RISCOS EXCLUÍDOS` will not
find it via semantic similarity. The corpus build raises no error when
this happens: the clause is valid per the [M1-07] schema (empty `text` is
allowed), so the gap is silent unless someone measures it — which is what
this document does.

## Method (2026-08-19 — second measurement, v6 corpus, real classifier)

`make parse` was rebuilt end to end after [M1-04c] and [M1-05b] landed. At
the time of sampling, the built corpus (`build/parsed_clauses.jsonl`/
`.parquet`, `schema_version=v1`, `clause_segmentation_version=v6`) held
**4469 clauses across all 30 documents** (up from 4266 at `v4` — the
boundary/heading fixes changed clause counts, not just accuracy).
Classification is now real: `LangchainClauseClassifier` via
`deepseek/deepseek-v4-flash-0731`, pinned to OpenRouter provider
`baidu/fp8` with fallback disabled, 10-way concurrency, 3-attempt retry
(5s apart) on transient failures — see [M1-08b]'s DoD for why the retry
and concurrency changes were needed before this rebuild could run
unattended.

**No `classification_version` constant exists in the codebase.** The
closest analogs recording which classifier produced a build are
`BuildManifest.llm_classification_enabled: bool` (`true` for both this
build and the stale pre-[M1-08b] one, so it alone does not distinguish
stub-era from real-classifier-era output) and whichever model string sits
in `.env`'s `LLM_MODEL_FAST` at build time. This is a documented gap, not
a silently invented field — a future issue could add one if build
provenance needs to be more precise than "read the git history of
`llm_classifier.py`."

**Sampling.** Same design as the first measurement, same `SAMPLE_SIZE=50`
and `SEED=42`, retuned only where the corpus's own composition forced it:

- **Stage 1 — a census.** The rule-assigned population shrank from 19 to
  **14** (`type_source=rule`) — the [M1-04c] boundary/heading fixes changed
  which clauses exist and which titles the deterministic rule pass
  matches, not just their accuracy. All 14 are included unconditionally,
  same as before.
- **Stage 2 — a stratified top-up of 36 clauses** (was 31), drawn from the
  LLM-assigned population via a quota over `(product_line, extraction_mode)`:
  CASCO/text 9 (unchanged), RCF-A/text 4, RCF-A/ocr 6, ASSIST/text 4,
  ASSIST/ocr 6, GAR.EST/text 4 (each +1 from the first measurement), CARTA
  VERDE/text 3 (unchanged). The +5 slots needed to keep `SAMPLE_SIZE=50`
  after the rule census shrank were spread one each across the five
  non-CASCO/non-CARTA-VERDE cells, preserving CASCO's already-largest
  quota, CARTA VERDE's already-thin quota, and both OCR cells' deliberate
  oversampling relative to their corpus share. See
  `scripts/sample_parsing_quality.py`'s module docstring for the exact
  reasoning.

Resulting sample: product lines CASCO 20 / RCF-A 12 / ASSIST 11 / GAR.EST 4
/ CARTA VERDE 3; extraction mode text 38 / ocr 12; type_source rule 14 /
llm 36; all 4 eras present (2004–2009: 12, 2010–2016: 6, 2017–2021: 8,
2022–2025: 24).

**Comparability with the first measurement's sample: not a matched pair.**
`clause_id` is derived from each clause's tree path
(`f"{document_id}:{path}"`), so the [M1-04c] boundary/heading fixes that
changed clause counts also shifted many `clause_id`s. Checked directly: of
the first measurement's 50 `clause_id`s, only **15 also appear** in the
second measurement's 50-clause sample. The two samples are independent
draws under the same stratification design, not a before/after view of the
identical 50 clauses — accuracy deltas below describe the corpus's overall
quality change, not a per-clause fix/regression diff.

**Validation.** Per this document's opening note, all 50 clauses were
validated by `google/gemini-3.7-flash` against the rasterized source PDF
pages (`scripts/validate_parsing_quality_sample.py`), not by a human. The
same three judgments as the first measurement were recorded: boundary
correctness, reference clause type, provenance correctness.

## Results (2026-08-19 — second measurement, v6 corpus, real classifier)

- **Boundary accuracy: 82.0% (41/50) — below the ≥90% M1 exit bar (FAIL).**
- **Type accuracy: 78.0% (39/50) — below the ≥85% M1 exit bar (FAIL).**
- **Provenance accuracy: 100.0% (50/50) — unchanged, still attached once
  per document from `manifest.csv`.**

Both bars moved sharply toward the target (boundary 60.0% → 82.0%, type
40.0% → 78.0%) but neither is met yet. See
[MILESTONES.md](../MILESTONES.md) for the explicit close/follow-up call
against these numbers.

### Confusion matrix (reference type × predicted type)

| reference \ predicted | coverage | exclusion | condition | definition | procedure | other |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| coverage | 3 | 0 | 1 | 0 | 0 | 0 |
| exclusion | 0 | 9 | 0 | 0 | 0 | 0 |
| condition | 3 | 1 | 12 | 0 | 0 | 0 |
| definition | 1 | 1 | 1 | 9 | 0 | 0 |
| procedure | 0 | 0 | 1 | 0 | 5 | 0 |
| other | 0 | 0 | 2 | 0 | 0 | 1 |

Unlike the first measurement, there is no `other` column collapse — the
classifier is genuinely discriminating between types now. The remaining
confusion is spread thin (1-3 per off-diagonal cell) rather than
concentrated in one failure. `condition` absorbs the most stray
predictions (from `coverage`, `exclusion` and `other`'s reference rows),
consistent with the failure modes below: `condition` is the classifier's
apparent default when a clause's true structural role (a definition-section
entry, a regulatory preamble) isn't legible from its text alone.

### Rule-assigned vs LLM-assigned type accuracy

| type_source | n | boundary accuracy | type accuracy |
| --- | ---: | ---: | ---: |
| rule | 14 | 85.7% (12/14) | 71.4% (10/14) |
| llm | 36 | 80.6% (29/36) | 80.6% (29/36) |

Directly against [M1-08]'s baseline (89.5% rule / 9.7% stub): the real
classifier's LLM-assigned type accuracy (**80.6%**) is now close to, and
in this sample slightly *above*, the rule pass's own accuracy (**71.4%**,
down from 89.5% — a small-n swing, 4 of 14 wrong on a 14-item census, not
evidence the rule table itself regressed). The 9.7% → 80.6% jump is the
headline number this measurement exists to report: replacing the stub with
a real classifier closed the vast majority of the type-accuracy gap
[M1-08] found.

### OCR-derived vs text-derived accuracy

| source | n | boundary accuracy | type accuracy |
| --- | ---: | ---: | ---: |
| text | 38 | 76.3% (29/38) | 76.3% (29/38) |
| ocr | 12 | 100.0% (12/12) | 83.3% (10/12) |

OCR-derived clauses now score *higher* on both axes than text-derived
ones — a reversal from the first measurement (text 65.0%/47.5%, ocr
40.0%/10.0%). This is a small-n result (n=12) and should not be read as
"OCR parsing is now better than text parsing" — more plausibly, the
specific OCR clauses drawn this time happen to sit in cleanly-segmented
regions, while the surviving boundary failures (below) concentrate in
deeply-nested numbered sub-clauses, a pattern more common in the
text-mode documents in this sample.

## The three worst failure modes (second measurement)

Ranked by frequency across the 16 of 50 clauses with at least one incorrect
judgment (full table in
[`eval/parsing_quality_results.md`](../eval/parsing_quality_results.md#failure-mode-frequency)):
`boundary_mismatch_llm` 9, `type_mismatch_llm` 7. (These tags are derived
programmatically from which of the three LLM judgments failed first —
see `scripts/validate_parsing_quality_sample.py`'s `derive_failure_mode_tag`
— not hand-assigned free text like the first measurement's tags, so the
vocabulary is coarser by design; the model's full reasoning for each
failure is in `boundary_notes`/`reviewer_notes`.)

### 1. Adjacent numbered sub-clauses merge into one node

The single largest cluster: a genuine heading between two or more
same-depth numbered siblings goes undetected, so the parser's clause
absorbs its neighbor(s) instead of splitting at the boundary. Present in
at least 5 of the 9 boundary failures.

**Examples** — sample #8, clause `8:a-condicoes-especiais-para-o-seguro-de-automovel/6/6.3`
(doc 8, Suhai, page 52): sub-clause `6.3` absorbs `6.4` and `6.5`. Sample
#22, clause `17:.../7.1.9` (doc 17, Bradesco, page 5): `7.1.9` absorbs
`7.1.10`. Sample #34, clause `24:6/6.1/6.1.2/6.1.3.3` (doc 24, MAPFRE,
page 25): `6.1.3.3` absorbs `6.1.4`, `6.1.5` and its own sub-items, `6.1.6`,
and `6.2` — five distinct clauses collapsed into one. Sample #46, clause
`29:4/4.3` (doc 29, BNP Paribas Cardif, page 6): `4.3` absorbs `4.4`.

**Downstream cost.** Each merge is a retrieval-and-citation error waiting
to happen: a query targeting `6.4`'s specific content retrieves `6.3`'s
chunk instead (or alongside it, diluted), and any citation naming `6.4`
has no clause id to point to, since it was never a node. This is the same
failure family [M1-04c] fixed for depth-1/2 headings (docs 13, 15, 20) —
this measurement shows it recurring one or two levels deeper, at
depth-3/4 numbered siblings the earlier fix didn't reach.

### 2. Clause content truncates at a page boundary

The parser correctly opens a clause but stops capturing its text at the
end of the page it started on, missing content that continues onto the
next page.

**Examples** — sample #6, clause `3:condicoes-particulares-clausula-especifica-apolice-coletiva`
(doc 3, AKAD/Argo, page 26): recorded as page 26 only, but items `E)` and
`F)` continue onto page 27. Sample #18, clause `15:coberturas-adicionais`
(doc 15, MAPFRE, pages 62–63): cuts off at the end of page 63 while clause
`2` continues onto page 64. Sample #47, clause `29:5` (doc 29, BNP Paribas
Cardif, page 6): `5. EXCLUSÕES GERAIS` is recorded as page 6 only, but
sub-items `5.3.4`–`5.3.7` continue onto page 7.

**Downstream cost.** Identical in kind to [M1-08]'s failure mode 3
(truncated boundaries) — a retrieval chunk missing its own continuation is
a chunk that answers a query about `5.3.5` with silence, since that text
was never captured anywhere. Unlike [M1-08]'s worst case (doc 13's
20-page/41,000-character merge, now caught outright by
`find_oversized_clauses`'s safeguard, see [M1-08b]'s DoD), these are
single-page overruns — cheaper individually, but more frequent.

### 3. Clause type is misjudged without its enclosing section's context

`LangchainClauseClassifier.classify` (and the parity-checking Gemini
validation pass) see only a clause's own title and text — never its parent
section's title. A clause that reads, in isolation, like an exclusion or a
coverage rule is still structurally a **definition** if it is one entry in
a `DEFINIÇÕES`/glossary section, or **other** if it is a regulatory
preamble before the first numbered clause — and nothing in either
classifier's input says so.

**Examples** — sample #32, clause `23:dano-estetico` (doc 23, Generali,
page 5): defines the term "Dano Estético" under "1. PRINCIPAIS TERMOS
UTILIZADOS"; because the definition's text mentions the condition is not
covered, it is classified `exclusion` instead of `definition`. Sample #44,
clause `28:.../2/2.25` (doc 28, Assurant, page 3): defines "Indenização"
under "2. DEFINIÇÕES"; classified `coverage` instead of `definition`
because the definition describes a payout. Sample #41, clause
`27:condicoes-gerais` (doc 27, Virginia Surety, page 1): a SUSEP regulatory
preamble preceding `Cláusula 1`; classified `condition` instead of
`other`.

**Downstream cost.** A definition clause labeled `exclusion` or `coverage`
pollutes exactly the metadata `docs/SCOPE.md`'s `compatible`/
`incompatible` verdict depends on filtering by — a downstream retrieval
step that pre-filters to `clause_type=exclusion` before checking coverage
compatibility would surface a glossary definition as if it were a real
policy exclusion. Structural context (parent title, section membership)
is not currently passed to either classifier; a follow-up would need to
thread `bundle_section`/parent title into the classification prompt.

## Method (2026-08-20 — third measurement, v7 corpus, deterministic only)

Unlike the first two measurements, this one is not a single before/after
snapshot. [M1-04d]'s vision-LLM boundary escalation was run for the first
time here, measured, found to be **net harmful**, and consequently left
disabled — and the improvement work that followed was carried out and
re-measured in the same pass rather than deferred to yet another issue.
Four scored states were produced; all four are reported below, because the
intermediate ones are the evidence for the decisions taken.

| # | state | boundary | type |
| --- | --- | ---: | ---: |
| 0 | [M1-08b] baseline (v6, no escalation) | 82.0% | 78.0% |
| 1 | v6 + escalation as [M1-04d] shipped it | 76.0% | 84.0% |
| 2 | v6 + escalation + safety guards | 80.0% | 80.0% |
| 3 | **v7 segmentation fix, escalation off (final)** | **84.0%** | **86.0%** |

**Two operational bugs had to be fixed before state 1 could even be
measured**, both real defects rather than run-specific mishaps:

1. **A stale cache silently reduced the whole escalation pass to a no-op.**
   [M1-04d] added `content_line_pages` (per-line page attribution, required
   by its correction step) to `Clause` without bumping
   `CLAUSE_SEGMENTATION_VERSION`, and `build_clause_tree.py`'s cache write
   is a no-op once a file exists — so every cached tree kept the field
   empty. The first full escalation run (1075 vision calls, $2.76, ~2h59m)
   applied **0 of the 252 corrections the model proposed**, 188 of them
   rejected specifically for "no per-line page attribution". Fixed by
   clearing and rebuilding the clause-tree cache; prevented from
   recurring by the `v6 -> v7` version bump, whose comment now states the
   rule: bump when the cached tree's *shape* changes, not only when the
   detection algorithm does.
2. **The validation script's resumability was keyed on sample position.**
   `validate_parsing_quality_sample.py` skipped any sample whose
   `validation_sample_{id:03d}.json` already existed. With this
   measurement's sample overlapping the previous one's, the first
   validation run silently reused all 50 stale, pre-escalation judgments —
   surfacing only because it "validated" 50 clauses in under a second
   instead of ~8 minutes. Fixed by keying the resume on a SHA-256
   `claim_fingerprint` over exactly what the model is shown (clause id,
   pages, predicted type, title, text excerpt), mirroring
   `boundary_escalation_cache`'s content-addressed pattern.

**Why escalation ended up disabled (states 1 and 2).** Because escalation
never restructures the tree, the state-1 and state-2 samples matched
[M1-08b]'s **50/50 on `clause_id`** — a genuine matched pair, allowing a
per-clause before/after diff rather than an inference from aggregate
numbers. That diff showed escalation applying 136 corrections corpus-wide
while producing, on the sample, **4 boundary regressions and 0 fixes**.
Root-causing them found a structural flaw, not a tuning problem: the
correction step reassigns whole pages of lines between neighbours, but a
page routinely carries several clauses (a glossary page in doc 23 carries
13). Two guards were added — page exclusivity (never move a page shared
with a third clause) and identity retention (never let a clause end up
holding none of its own original lines) — and they revealed the size of
the problem: **only 28 of the 136 corrections were sound**; 95 were
blocked by exclusivity alone. With the guards in place (state 2)
escalation still produced 1 regression and 0 fixes against [M1-08b]. A
mechanism with no measured upside and a measured downside should not run,
so the final state has it **off**, and it stays opt-in (`make
escalate-vision-boundaries`, never part of `make parse`). The guards
remain in the code so that any future re-enablement starts from the safe
behaviour.

**The change that actually helped (state 3).** [M1-08b] and this issue both
identified adjacent numbered-sibling merges as the largest boundary-failure
cluster, and [M1-04d] named it a target — but escalation could never have
fixed it: these merges are *intra-page*, while the correction step works at
page granularity, and a vision-proposed split is deliberately never
auto-applied. The real cause was in the deterministic detector. Doc 8 p52
typesets `6.3` bold (bold_fraction 0.99) and its own siblings `6.4`/`6.5`
in the body font (0.03), so `_detect_heading`'s bold gate swallowed them.
`_detect_sibling_continuation` adds a font-independent fallback: a line
opening with exactly the numbering label that follows an open clause's is a
heading however it is typeset. Deliberately *not* gated on vertical
spacing — docs 17 and 24 set sub-clauses at exactly the ordinary line pitch
(15.72–15.84pt against a 15.8pt modal gap), which is also why the main loop
never applies that gate to bold numbered headings. This split **4 of the 5**
sampled sibling merges (docs 8, 17, 22, 29; doc 24 partially) and grew the
corpus from 4469 to **4925 clauses (+456, +10.2%)** across 22 documents,
with no document losing clauses and all orphan ratios unchanged or
improved.

**Sampling.** Same design, `SAMPLE_SIZE=50`, `SEED=42`, same `QUOTAS`, rule
census still 14. Resulting sample: CASCO 20 / RCF-A 12 / ASSIST 11 /
GAR.EST 4 / CARTA VERDE 3; text 38 / ocr 12; type_source rule 14 / llm 36;
all 4 eras (2004–2009: 12, 2010–2016: 6, 2017–2021: 9, 2022–2025: 23).

**Comparability.** States 1 and 2 matched [M1-08b] 50/50 on `clause_id`.
The final state does not: splitting 456 previously-merged sub-clauses
necessarily shifts paths, so the final sample overlaps [M1-08b]'s by
**23/50** — better than the [M1-08]→[M1-08b] transition's 15/50, and for a
substantive reason rather than a version bump alone.

**Validation.** All 50 clauses validated by `google/gemini-3.7-flash`
against the rasterized source PDF pages, per this document's opening note.

### Residual analysis: 6 of 8 boundary failures are a metric artifact

Every remaining boundary failure was checked against the corpus's own tree
structure — specifically, whether the clause has children covering the
pages the validator says are missing:

| # | clause | own pages | children | subtree pages | verdict |
| --- | --- | --- | ---: | --- | --- |
| 9 | `9:12/12.2` | 38–39 | 0 | 38–39 | genuine defect |
| 16 | `15:condicoes-gerais` | 13 | 33 | 13–59 | parent-vs-subtree |
| 18 | `15:coberturas-adicionais` | 62–63 | 9 | 62–75 | parent-vs-subtree |
| 19 | `15:13-danos-aos-vidros-top-plus/22` | 113 | 4 | 113–114 | parent-vs-subtree |
| 22 | `18:3` | 4 | 55 | 4–11 | parent-vs-subtree |
| 43 | `27:.../3/3.2` | 22 | 1 | 22–23 | parent-vs-subtree |
| 46 | `29:.../21.3/21.3.4` | 17–18 | 0 | 17–18 | genuine defect |
| 47 | `29:25-atualizacao-de-valores/2` | 21 | 1 | 21–23 | parent-vs-subtree |

The six "parent-vs-subtree" rows are all the same shape: the validator
reports the clause as truncated because its section's content continues
onto the next page — but that continuation is held by the clause's own
**child nodes**, exactly where a hierarchical parser should put it. Sample
#22 is the clearest: `18:3` ("Definições") is marked truncated for not
covering `3.4`–`3.10`, which exist as 55 separate child clauses spanning
pages 4–11.

**This is a definitional mismatch in the metric, not a parsing error, and
it is self-defeating: the better the parser splits a section into its real
sub-clauses, the more parent nodes it creates whose own page range is
narrower than the whole section's, and the more the metric penalizes it.**
It is a plausible part of why fixing 4 of 5 sibling merges moved boundary
accuracy only 82.0% → 84.0%. The two genuine defects are a one-page
front-edge misalignment (#9, recorded 38–39 against a true 37–38) and one
surviving sibling merge (#46, `21.3.4` absorbing `21.3.5`).

The metric has **not** been redefined here to make the number look better.
Judging a hierarchical parser's node against a flat "whole section" span is
arguably measuring the wrong thing, but changing what "≥90% correct clause
boundaries" means mid-milestone, and breaking comparability with [M1-08]
and [M1-08b], is a decision for the project owner to take explicitly — see
[MILESTONES.md](../MILESTONES.md).

## Fourth state (2026-08-20) — boundary criterion corrected, pre-registered

The residual analysis above found that 6 of 8 boundary failures were the
metric judging a parent node against its whole subtree's span. The project
owner's explicit decision was to correct the criterion rather than leave a
number that is known to understate quality, or degrade the data model to
satisfy the old one.

Exactly one thing changed: `build_validation_message`'s boundary question
now states that sub-clauses are separate records and asks the model to
judge only this record's own span. No other prompt text, no sampling
change, no corpus change, no code change outside that paragraph.

## The worst failure modes (third measurement)

Ranked across the 14 of 50 clauses with at least one incorrect judgment:
`boundary_mismatch_llm` 8, `type_mismatch_llm` 6.

### 1. Parent clauses judged against their whole subtree's span

Six of the eight boundary failures, covered in full in the residual
analysis above. Not a parsing defect; a mismatch between how the parser
models hierarchy and how the validation prompt asks about boundaries.

**Downstream cost.** None directly — the content is captured, in the child
node where it belongs. The cost is to the *measurement*: it understates
boundary quality and does so more as segmentation improves, which makes the
≥90% bar progressively harder to reach for reasons unrelated to parsing.

### 2. Clause type is misjudged without its enclosing section's context

Now the largest genuine cluster (6 of 14 failures), unchanged in kind from
the second measurement. Neither `LangchainClauseClassifier` nor the
validating model sees a clause's parent-section title, so a clause whose
true role depends on its enclosing section is misread.

**Examples** — sample #31, `23:condicoes-gerais` (Generali, page 4): a
glossary entry under "1. PRINCIPAIS TERMOS UTILIZADOS", classified
`condition` instead of `definition`, the validator noting the parser "was
likely misled by the term name". Sample #41, `27:condicoes-gerais`
(Virginia Surety, page 1): a SUSEP regulatory preamble, classified
`condition` instead of `other`. Sample #13, `13:.../22` ("FORO
COMPETENTE"), classified `procedure` instead of `condition`.

**Downstream cost.** Unchanged: this pollutes the `clause_type` metadata
`docs/SCOPE.md`'s verdict logic filters by. The fix is known and
unaddressed — thread `bundle_section`/parent title into both the
classifier's and the validator's prompts.

### 3. Residual single-clause boundary defects

Two cases, both genuine and both narrow: a one-page front-edge
misalignment (#9, `9:12/12.2` recorded 38–39 against a true 37–38) and one
sibling merge the numbering-continuity fallback did not catch (#46,
`21.3.4` absorbing `21.3.5`, the same partial-coverage limitation seen on
doc 24's `6.1.6`).

**Downstream cost.** The familiar one: a query targeting the absorbed
sub-item retrieves its neighbour's chunk, and a citation naming it has no
node to point to. At 2 of 50 this is now a tail case rather than a cluster.

## Known limitations

Third-measurement-specific:

- **The boundary criterion was corrected mid-issue, on the project owner's
  explicit decision**, after the residual analysis showed 6 of 8 failures
  were the metric judging a parent node against its whole subtree. The
  correction was pre-registered with a falsifiable prediction before
  re-running, and both deviations from that prediction are reported in the
  fourth state above rather than absorbed. Consequence to keep in mind when
  reading this document: **98.0% and the earlier 60.0%/82.0%/84.0% are not
  a single series** — the question changed.
- **One boundary judgment (#9) flipped between runs for reasons unrelated
  to the change under test**, on a printed-page-label vs. PDF-page-index
  disagreement. The conservative reading of the headline is 96.0% (48/50).
  This also identifies page-numbering ambiguity as a variance source in the
  validation method that no earlier measurement had isolated.
- **The type figure moved when only the boundary question was meant to
  change** (86.0% → 92.0%), because the added hierarchy context reframes
  what each record is. The robust claim is that type accuracy clears the
  ≥85% bar under **either** framing.
- **No second-rater or self-agreement control exists.** Every judgment in
  the second, third and fourth states comes from a single
  `google/gemini-3.7-flash` pass. Two run-to-run flips were observed
  directly in this issue (#9 above, and `15:coberturas-adicionais` between
  two earlier states with identical content), so the run-to-run variance of
  this method is non-zero and unquantified. Re-running the validator twice
  over one sample and publishing the self-agreement rate would quantify it
  without needing a human rater.
- **[M1-04d]'s vision escalation is disabled, on evidence.** It applied 136
  corpus-wide corrections of which only 28 were structurally sound, and
  produced 4 boundary regressions and 0 fixes on a matched-pair sample (1
  regression, 0 fixes once guarded). Its correction step reassigns whole
  pages between neighbours, which is unsound wherever a page carries more
  than one clause — most of this corpus. The guards
  (`_pages_shared_with_others`, identity retention) stay in the code so any
  future re-enablement starts safe, but the pass remains opt-in and off.
- **The numbering-continuity fallback is not exhaustive.** It split 4 of the
  5 sampled sibling merges; doc 24's `6.1.6` and sample #46's `21.3.5` were
  not recovered, so a residual tail of this failure mode remains.
- **It trades a false-negative risk for a false-positive one.** Dropping the
  vertical-spacing gate means a wrapped body line beginning with exactly
  the successor label would be promoted to a heading. No instance appeared
  in the corpus evidence behind this measurement, and the +456 new clauses
  were spot-checked as genuine numbered sub-clauses, but this is an
  accepted risk rather than an impossibility.
- **Two operational bugs were found and fixed mid-measurement** (stale
  `content_line_pages` cache; position-keyed validation resumability) —
  see the Method section. Both were real defects that silently corrupted a
  measurement, and both are now fixed in code rather than by manual
  cache-clearing.
- **The committed cost report reads $0.00 and 0 calls, which is true but
  deeply misleading in isolation.** It records only the last escalation
  run, by which point all 1078 reviews were served from the
  content-addressed cache. Actual spend across the three runs was
  **1100 vision calls, ~$2.85, ~3h04m**: $2.76/1075 calls on the run
  invalidated by the stale-cache bug, $0.08/25 calls re-running after the
  fix, $0.00 on the final guarded run. The report has no field for
  superseded runs, so the breakdown lives here.
- **Small-n statistics persist.** The rule census (n=14), OCR cell (n=12)
  and the residual-failure buckets (2 genuine defects) are small counts;
  read them as directional.

Second-measurement-specific:

- **The classifier gap (first measurement's failure mode 1) is closed.**
  The follow-up scoped in the first measurement's "Known limitations"
  ([M1-05b]) has landed and been measured — see the second measurement
  above.
- **Boundary and type accuracy still miss the M1 bar** (82.0%/78.0% vs.
  ≥90%/≥85%) — see [MILESTONES.md](../MILESTONES.md) for the explicit
  close/follow-up call.
- **The second measurement's validation is LLM-automated, not
  human-reviewed** — see this document's opening note. Unlike a human
  reviewer, the validating model shares failure modes with the models this
  project already depends on (it can also misjudge an ambiguous case,
  particularly the same "no parent context" gap the classifier itself has
  — see failure mode 3 above, which the validating model still correctly
  flagged as a mismatch precisely because its prompt states the reference
  type should be judged from the clause's own content, independent of
  section headings not shown to it). No independent second-rater agreement
  check exists for this measurement.
- **OCR now scores higher than text-mode on both axes (100%/83.3% vs.
  76.3%/76.3%), reversing the first measurement's finding** (40%/10% vs.
  65%/47.5%). Read this as a small-n (n=12) artifact of which specific OCR
  clauses this draw happened to include, not evidence that OCR parsing
  itself improved between measurements — nothing in [M1-04c]/[M1-08b]
  changed the OCR heading-detection path.
- **Small-n statistics.** The rule-assigned (n=14) and OCR (n=12) cells
  remain modest sample sizes; their figures should be read as directional.

Structural, applies to all three measurements:

- **No rule-assigned OCR clauses exist in the corpus** to measure the
  intersection of those two conditions.
- **Author-curated sampling.** All three measurements' 50-clause samples
  were drawn by the same person who built the parser being evaluated, per
  the same caveat documented in
  [`DATA_SOURCES.md`](DATA_SOURCES.md#known-limitations) for the golden
  set — this is separate from *who validated* each sample (human for the
  first measurement, an LLM for the second and third, per the note above).

First-measurement-specific (superseded, kept for the historical record):

- **OCR quality was a compounding, not just an additive, problem** —
  boundary accuracy (not only type accuracy) was measurably worse for
  OCR-derived clauses (40% vs. 65%) at the time of the first measurement.
  Reversed in the second measurement, above.
