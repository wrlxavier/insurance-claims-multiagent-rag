# Synthetic claim set (M2-04)

`claims.jsonl` holds the end-to-end test inputs for this project: claim
narratives, not questions — free text as a policyholder would write it, which
the (future) intake node has to make sense of.

## These are entirely synthetic

**No real policyholder data was used to produce this file, in any form.**
Every narrative was generated by an LLM from a scenario built out of the
corpus's own filed product conditions (`data/policies/`) — never from a real
claim, a real customer interaction, or any external dataset. Nothing here
describes a real event, a real person, or a real vehicle.

Every narrative was also written under an explicit, enforced prohibition on
anything resembling personal data, even fabricated: no names (the claimant
and any other party are referred to generically — "eu," "minha esposa," "o
outro motorista"), no CPF/RG or other document numbers, no license plates, no
specific addresses (a city is fine; a street and number is not). A regex
safety net (`scripts/pii_safety_net.py`) scans every narrative for
plate/CPF/RG patterns and a loose proper-name heuristic before a row is
drafted and again before it is finalized here — any hit blocks that row
rather than silently promoting it.

## How they were produced

The same three-layer authoring flow this project already uses for the golden
set (see `docs/EVALUATION.md`), adapted for claim narratives instead of
questions:

1. **Deterministic scenario selection** (`scripts/synthetic_claims_selection.py`,
   no model involved) picks, for each claim: a target document, the source
   clause(s) that justify the label, and the verdict itself —
   `compatible` (a clean instance of a covered peril), `incompatible` (the
   narrative trips a specific exclusion clause), or `insufficient_information`
   (a fact the applicable clause depends on is deliberately omitted from the
   narrative). Verdict and clause selection are always code, never the LLM's
   call.
2. **LLM narrative drafting** (`scripts/draft_synthetic_claims.py`, OpenRouter
   `google/gemini-3.7-flash` via the `google-vertex/global` route) writes the
   actual claim text a policyholder would submit — informal Brazilian
   Portuguese, an imprecise date, at least one irrelevant tangential detail —
   for the scenario Layer 1 already resolved. The model only phrases the
   narrative; it never decides the verdict or which clauses apply.
3. **Human review** — every drafted row was checked against the M2-04
   Definition of Done and approved before promotion
   (`eval/synthetic_claims_draft.csv` carries the row-by-row draft and review
   trail: `review_verdict`, `review_correction`, `approved`).
   `scripts/finalize_synthetic_claims_from_review.py` promotes `approved`
   rows into `claims.jsonl`, and `scripts/validate_synthetic_claims.py`
   checks the result structurally (every `document_id` and
   `reference_clause_ids` entry resolves against the real corpus, every
   `claim_id` is unique).

Reproduce with:

```
PYTHONPATH=app/src uv run python scripts/draft_synthetic_claims.py --dry-run   # scenario counts, no LLM calls
PYTHONPATH=app/src uv run python scripts/draft_synthetic_claims.py             # drafts eval/synthetic_claims_draft.csv
PYTHONPATH=app/src uv run python scripts/finalize_synthetic_claims_from_review.py  # promotes approved rows
PYTHONPATH=app/src uv run python scripts/validate_synthetic_claims.py         # structural validation
```

## Schema

One JSON object per line, validated by
`infrastructure.evaluation.synthetic_claims_schema.SyntheticClaim`:

| Field | Description |
| --- | --- |
| `schema_version` | Schema contract version. |
| `claim_id` | `{expected_verdict}-{seq:03d}`, e.g. `compatible-001`. Unique. |
| `document_id` | The target document's `id` in `data/policies/manifest.csv`. |
| `narrative` | The claim text itself, in Brazilian Portuguese. |
| `reference_clause_ids` | The clause(s) in the target document that justify the label. |
| `expected_verdict` | `compatible` \| `incompatible` \| `insufficient_information` — this project's one verdict vocabulary (see `docs/SCOPE.md`). |
| `missing_fact_type` | Set only when `expected_verdict` is `insufficient_information`: which fact the narrative deliberately omits (`ambito_geografico`, `uso_do_veiculo`, `data_evento_vigencia`, `valor_franquia_limite`, `tipo_evento_condicao`) — the ground truth a future clarification loop (M4-03) should reproduce in its own `missing_information` output. |
| `notes` | The reviewing author's own rationale, where recorded. |
| `authored_at` | Date the row was approved, `YYYY-MM-DD`. |

## Coverage

40 claims (DoD floor: ≥30), 13 of them `insufficient_information` (DoD floor:
≥10), spread across all five product lines rather than only `CASCO`:

| Product line | Claims |
| --- | --- |
| CASCO | 12 |
| RCF-A | 9 |
| ASSIST | 9 |
| GAR.EST | 6 |
| CARTA VERDE | 4 |

Every claim in this set targets its own, correctly-matched product line —
e.g. an ASSIST claim tests ASSIST's own coverage/exclusion clauses. Claims
deliberately aimed at the *wrong* product line (an own-damage claim submitted
against a liability-only document, say) are a separate dataset, scoped to a
later issue (M2-05), so the two sets don't overlap.
